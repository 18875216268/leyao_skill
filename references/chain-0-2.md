# 理解阶段（chain-0-2）：0 请求理解 → 1 工作包理解 → 2 需求确认

> 总览与两门判据见 `references/chain-overview.md`。本页承载理解阶段各步**执行详述**（入口判据 / 关键机制 / 出口产物）。

## 理解阶段循环拓扑（0↔1↔2 · 分层不互扰）

三阶段各管一层、产物单一：0 语义层产 intent / 1 材料层产 workspace-package / 2 需求层产 resolved requirement。跨层只走反馈信号，不混产物。六条双向边：
- `0→1` 意图喂读（读什么/重点看什么）；`1→0` 材料回馈（材料与意图冲突 / 材料揭示新意图）；
- `1→2` 材料事实（有什么/缺什么）；`2→1` 缺口回馈（还缺什么材料）；
- `0→2` 意图约束（核心意图 = 需求锚）；`2→0` 需求回查（需求不清时回溯意图是否读准）。

**节点决策四选项**：`自审 → 继续 / 重启本阶段 / 重启子步骤 / 回退上游阶段`。

## 0. 请求理解（语义层 · 把用户的话读准）

### 0.1 接收信息
原始输入，不加工不猜测。

### 0.2 语义剖析
拆解语义（5W1H 结构化：What 目标/操作 · Why 动机 → 长期意图信号 · Who 范围 · When/Where 周期/场景 · How 交付物）。用户本轮要求优先；临时要求不自动变成长期规则；长期意图信号沉淀 core 候选。

### 0.3 语义三分（确定性筛选 · 三类互斥）
- **排除无关**：错字/口误/歧义/干扰项 → 消除，不进入意图；
- **候选可能**：意图不清晰 → 列出全部可能性，标注置信度；
- **确定相关**：意图清晰精准 → 锁定核心意图。

自问：这句里哪些是噪声？哪些可能有别的意思？哪些是唯一肯定的？

### 0.4 分类判断（用户反馈交互——同一请求反复出现要区分性质；判断前先预载三源——本地 K1 近期相似 / 云端两库（注入/会话）/ ask-log 历史，见「知识前置」；只对 0.3 的"确定+候选"分类）：
- 首次提出/新主题 → 正常进主链；
- 与近期历史同指纹且无变化词（同 Run 或短间隔重复，ask-log 指纹比对）→ 标记「可能不满，需重新解决，不复用旧答案」（resolve 会跳过早停重新解决）；
- 含时间/范围变化词（本周/上季度/XX 客户）→ 新需求变体（正常，新 cache key）；
- 本轮明确改变 → 本轮优先；用户片段式续接先判定是「确认」还是「纠正」，不默认是确认。

### 0.5 歧义消解（澄清三问：Clarify When Necessary / 信息增益）
- 不确定性高才澄清（不打断清晰需求）；澄清优先问信息增益最大的维度（目标/范围/周期）；
- **确认前自证（思考协议⑤最小确认落地）**：先说明"已推过什么、已查过什么（协议前四步）、只差哪一项"再问——让确认成为填空而非问卷；
- 确认时积极倾听式复述（「您的意思是……对吗？」）→ 写入 intent anchor；
- 歧义根因可 5Why 追问（克制，追问不适换 5W1H 问场景）；仍不清 → 走「卡点调度」BRF 或暂停确认。

### 0.6 反馈接收（来自 1/2 的疑惑信号）
自问"语义剖析漏了/错了吗" → 重启 0.2/0.3 对应子步骤。

## 1. 工作包理解（材料层 · 把工作包读透）

### 1.1 梳理结构（大拆小）
工作包递归拆解到"不可再分"单元（文件/区域/表格 → 字段/段落/数值）。拆不动的单元才是判断单位。探查范围：目录、输入材料、控制文件、模板、数据、历史成果、脚本、配置、文件角色和关系；工作簿、文档、数据文件和历史成果理解都是本层按需能力。

### 1.2 整理分类（五性质）
每个单元判定**性质**，性质决定"怎么用"：
- **指令类**（要求做什么）→ 任务本体，驱动执行；
- **参考类**（提供依据）→ 取依据，不是任务；
- **模板类**（规定格式）→ 套格式；
- **数据类**（输入）→ 计算输入；
- **历史类**（过往成果）→ 先证明后引用（可能过时/误导）。

### 1.3 细读分流（信息结构驱动）
- **有规律**（结构规整：表/模板/日历）→ 结构优先、找规律并验证；
- **无规律**（自由文本/异构材料）→ 全量分析。

生成 `workspace-package.json`，不因低置信推断移动或覆盖文件。理解材料时遇不认识的业务术语/指标口径 → 走「卡点调度」调 BRF 澄清后再继续（理解门）。

### 1.4 关联性分层（四级 · 层层递进）
按"**材料 → 部分 → 内容**"逐层标注：**必须要 / 可能要 / 仅参考 / 不需要**。重点优先：先理解影响度（变了结果会变吗）+ 关联度（与其他单元关系）最高的项；相似但非本体的项显式隔离（相似 ≠ 适用）。

### 1.5 材料完整性核验（思考协议②完整性核验落地 · 输入材料闭合四判据）
读材料时按四判据检查信息集闭合——任一不过**先补齐**，补不齐才走歧义消解（说明缺的是哪块边界）：
- **配平**：汇总 = 明细之和？总数对得上吗？
- **多源一致**：不同来源对同一事实说法一致吗？不一致以哪个为准、为什么？
- **边界闭合**：有无未读部分（下一页/下一张表/后续区域/折叠内容）？
- **事实/推断分离**：哪些是**看到的**、哪些是**推断的**？推断标注依据。

> 与第 2 步「四性自检·完整」分工：本步管**输入材料**信息闭合（材料读全没），第 2 步管**需求描述**规格完整（需求写全没）——对象不同不重叠。

### 1.6 角色确认点（反馈机制 · 不确定才问）
识别出**关键角色**（`output_template` 决定报告格式、`control_file` 决定处理规则）且 confidence 不足（< 0.9）时 → 生成**角色确认清单**给用户核对（列出文件、判定角色、confidence、疑点），确认后写入 workspace-package.json（角色 + confidence + 确认状态）；高置信角色直接采用不打扰。低置信/未知文件只列 reuse 建议与未分类清单，不移动。

### 1.7 反馈（双向）
- **发往 0**：材料发现与 0 的意图冲突/补充 → 发信号 → 0 自审重启对应子步骤；
- **接收 2**：缺材料/漏项 → 自问"细读漏了吗/分层错了吗" → 重启 1.3/1.4。

## 2. 需求确认（需求层 · 任务与现状对齐）

### 2.1 整理任务
单任务：要做什么？多任务：逐任务列出"任务N要做什么"。

### 2.2 现状盘点
每个任务：**有什么 / 没有什么 / 还缺什么**。

### 2.3 获取更多
缺口 → 内部获取优先（材料细读 / 知识检索，先取后求）；内部穷尽才外部。

### 2.4 状态判定（穷尽自审链 · 思考协议⑤最小确认在需求阶段的细化）
- **清晰** → 进入 2.5 规格确认；
- **不清晰** → 顺序自审：①**有遗漏吗**（回 1.4/1.5 材料层查漏）→ ②**内容够吗**（回 2.3 获取补内容）→ ③**内部都查了吗**（两库/知识前置已穷尽，网络层前都获取）→ ④仍不清 → **反馈上游**（0 意图读准了吗 / 1 材料读透了吗）触发对应阶段重启 → ⑤上游确认无误 → **才联网或询问用户**（升级是最后一步，不是默认动作）。

### 2.5 规格确认（四性 + 验收 + 优先级）
将用户意图与工作包事实合并为 resolved requirement。关键字段、范围、公式、数据源、模板映射和外部副作用存在歧义时暂停确认；公式/数据源/指标口径歧义先调 `resolve --need-type caliber` 澄清，再确认（理解门）；确认时**积极倾听式复述**（开放问题探索、封闭问题确认事实）；确认内容写入 intent anchor。

**确认标准（IEEE 830 简版 · 确认前四性自检）**——任一不过 → 继续澄清，不得推进：
- **无歧义**：每个需求只有一种解释（术语唯一）；
- **完整**：字段/范围/约束/数据源/模板映射/外部副作用全覆盖；
- **可验证**：每个需求有明确判定方式（能回答"怎么检查它达成了"）；
- **一致**：需求之间无冲突。

**验收标准（Definition of Done · 喂 7b 交付门）**：每个需求/交付物写验收标准——**可测**（Given-When-Then 或 pass/fail 清单）· **结果导向**（描述达成状态非实现步骤）· **可量化**（有明确阈值）· **独立**（单条自洽）。写入 `anchor.acceptance`；7b 交付门逐项检查。

**优先级分级（防 scope creep 边界）**：每个需求标 必需（不满足不可接受）/ 条件（有则更好）/ 可选——不在验收标准里的改动视为新需求，不悄悄混入本轮。

### 2.6 sign-off
全部确认完成后 `anchor.sign_off: unconfirmed → confirmed`（签名语义，审计可溯）。
