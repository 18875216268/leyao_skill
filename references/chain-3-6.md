# 规划阶段（chain-3-6）：3 任务规划（3a/3b/3c）→ 4 抽象流程 → 5 能力与工具 → 6 可执行流程

> 总览与两门判据见 `references/chain-overview.md`。本页承载规划阶段各步**执行详述**（含 3/7 拆分子步的入口与出口判据）。

## 3a. 交付物锚定

创建或定位 WorkOrder；确定四类 Deliverable 清单（`report` 报告、`retrospective` 复盘、`template` 模板、`other` 其它）作为**终点锚**——列 `anchor.deliverables`（不增不减，第 2 步验收标准逐条对应）。交付物通过 bindings 多对多引用 Task 已确认结果，不在 Task 中双写报告关系。

**锚定判据（3a 出口）**：
- 每交付物有类型/周期/scope/template_id（正交字段，不扩张固定分类）；
- deliverables 与 `anchor.acceptance` 一一对应（验收标准覆盖全部交付物）；
- 无交付物指向未定义边界（scope 模糊 → 回 2 步澄清）。

## 3b. Task 拆解

按能力边界把 deliverables 拆为原子 Task；每 Task 先建 draft（激活门未过不激活）。

**粒度法则（原子 Task 四判据，全满足才算"原子"）**：
- **单 Run 可完成**：一次执行跑完、中途不换目标，否则继续拆；
- **输入输出确定**：输入来源（raw/clean/analysis/上游 Task 产物/外部数据源）与输出类型路径明确；
- **可独立验收**：有明确交付判据，不依赖兄弟 Task 中间状态即可判定成败；
- **MECE 不重不漏**：兄弟 Task 互不重叠，合并后 100% 覆盖 intent anchor 的 deliverables；
- 反例护栏：过大（Run 内需切目标）→ 拆；过小（无独立验收价值的碎片）→ 并入相邻 Task。

**拆解四步（自上而下 + 复用对碰）**：
1. **定交付物清单**：直接引 3a 的 `anchor.deliverables`（终点锚，不增不减）；
2. **反推顶层 Task**：每交付物对应主 Task；先查既有 WorkOrder 长期 Task，scope 匹配即复用，不重复建；
3. **按能力拆到原子**：沿能力边界拆（取数/清洗/计算/渲染/外发），每子 Task 过粒度四判据 → 100% 覆盖；
4. **依赖边 + 验证点**：按数据流反推 dependencies（产出 → 消费），逐 Task 写 validation（衔接 3c）。

**拆解出口（3b 判据）**：所有 Task 过粒度四判据；合并覆盖 = deliverables；无重复建（复用对碰完成）。

## 3c. 验证点与依赖

为每个 Task 绑定验证判据与依赖边，让计划"可严格消费"。

**验证点分级（Task.validation 规范化 · 衔接 2/4/7b 不双写）**：
- **交付判据（DoD）**：Task 出口判据，引用/派生自 `anchor.acceptance` 对应条（不复制需求文本）→ 7b 交付门逐项检查；
- **过程检查**：长 Task 内部里程碑（如"清洗后行数 = raw 行数、缺失率 < 5%"）→ 第 4 步抽象流程细化；原子 Task 可无；
- **激活门**：`validation` 仍为占位值（`Define validation before activation`）→ Task 不得激活（draft → active）。

**依赖边（数据流反推 · 无环）**：按数据流反推 dependencies（产出 → 消费），`orchestrator add-edge` 注册；依赖环检测（plan 时报环）→ 回 3b 重排。

**粒度权衡 + 再规划（执行中触发）**：
- 默认**偏细**（可独立验收优先、失败定位准），执行中发现过细再合并；
- **5 触发**：① 任务失败 ② 新信息（材料/口径新出现）③ 需求变化 ④ 资源约束 ⑤ 依赖阻塞；
- **两级处理**：先诊断（卡点调度/资源门）→ **局部调整**（改依赖/补 Task/改验证，不动顶层）→ **重新规划**（顶层结构变，重跑拆解四步）；
- **与阶段回环的关系**：再规划 = 回退链的特例（根因定位为 3b/3c 时触发，见 `references/governance.md`「阶段回环」）——本步只做结构调整，不做归因；③ 需求变化回第 2 步重签 sign-off；④ 资源约束走「规划-资源循环」；① 任务失败先走 7a 失败策略。

## 4. 抽象流程

先定义每个 Task/Deliverable 要完成的步骤、输入输出、依赖、验证和失败策略，不绑定工具。

**逻辑步骤五要素（每步齐全）**：输入来源（raw/clean/analysis/上游步骤 output_id/外部数据源）· 输出形态（类型+落点区）· 步骤序列（含并行声明）· 验证判据（引用 Task.validation，不复制）· 失败策略。

**流程模式声明（五工作流模式 · 先选形状再写步骤）**——每个 Task 先声明流程形状并给选型理由：
- **chaining 固定串行**：步骤可预先命名、顺序固定（默认）；
- **parallelization 并行**：多个独立步骤可并发（如多源取数），显式声明并行组；
- **routing 分流**：输入分类后走不同处理路径（按数据形态/口径分支）；
- **evaluator-optimizer 迭代改进**：有明确判据且迭代确有增益（如复盘草稿自检）；
- 不选 agent 自治循环（orchestrator-workers/ReAct）——任务已在 3b 拆为原子 Task，步骤可命名时保持 workflow 优先（能命名步骤就硬编码流程形状）。

**数据流引用（占位符式 · 计划可严格消费）**：每逻辑步骤输出给稳定 `output_id`（如 `step2.clean_rows`），下游步骤按 id 引用，不重复描述中间产物；执行时 manifest/lineage 按 id 记录。抽象流程因此可校验：每步输入都能追溯到上游输出或外部源。

**失败策略分级（渐进式失败层级 · 最后一层才是请示）**：每步骤定义失败后按级处理——
1. **自纠正**：报错信息回喂模型，修正参数/路径后重试（仅限可安全重试的幂等操作）；
2. **降级**：换数据源/缩小范围/产出部分结果（部分完成也交付，失败项显式标注）；
3. **升级**：走「卡点调度」BRF、暂停向用户确认，或启动「阶段回环」按根因回退（涉及覆盖/外发/口径改变先确认）。
fallback 属第 5 步资源级替代（这个工具不行换哪个），本步失败策略只管流程级处置（这一步做不出来怎么办）——层级不同不重复。

## 5. 能力与工具规划

按步骤需求选择工具、技能、脚本和数据源：能力经 `capabilities.py` 在外部 work-dir 运行时注册（含 BRF 卡点解决能力，用 `python brf/brf.py register-capability --work-dir <dir>` 一键注册）；比较适配度、准确性、速度、格式保真、审计性和副作用，生成 fallback 和确认要求；遇到知识/口径卡点直接走「卡点调度」调 BRF。盘点已掌握资源能否支撑全流程执行；缺口按「规划-资源循环」边规划边补（能找到→原规划；找不到→换工具/换口径/降级/确认），直到资源到位、方案可落地。

**选型四步（结构化选型）**：
1. **列能力清单**：按第 4 步各逻辑步骤列出候选（工具/技能/脚本/数据源，可 `tools_discovery` 动态发现本机技能）；
2. **六维比较**：适配度/准确性/速度/格式保真/审计性/副作用；
3. **收敛候选**：候选 > 5 先按相关性过滤（工具过多模型选错率上升），保留最相关 1-5 个；
4. **选择 + fallback 链 + 确认要求**：主选 + 备用链（Primary → Fallback1 → Fallback2）+ 副作用/联网/登录/外发确认。

**能力描述评估判据（从 LLM 视角读工具）**：评估候选能力时确认其描述回答——做什么 + 何时用 + 何时不用 + 参数值域/格式 + 返回结构（结构化、带错误信息与修正建议）；描述不清的能力先补写再采用；执行器返回须结构化可回喂（报错喂回模型自纠正，见第 4 步失败策略）。

## 6. 可执行流程

绑定具体执行器、版本、路径、参数、检查点、验证项和权限。工具规划回答"用什么"，可执行流程回答"如何落地"。

**执行计划结构（逐条映射第 4 步逻辑步骤，一条不落）**：每逻辑步骤 → 执行器（脚本/命令/技能，含版本）+ 具体路径 + 参数（含 `tool_choice`：auto 自主 / required 必用工具 / 指定工具）+ 输出落点（对应第 4 步 `output_id`）+ 权限与确认要求。逻辑步骤的验证判据在此绑定为「验证动作」（跑什么命令、比对什么字段）——判据与动作不重复。

**检查点落点规则（承接 3c 过程检查 · 三处不漂移）**：3c 定义「过程检查」（什么值得查）→ 本步落「执行时点」（在哪步、跑什么验证动作）→ 7a 执行时写 checkpoint 记录结果。落点纪律：**状态变更前**记 checkpoint（防崩溃后重复执行产生重复副作用）；不可逆动作（外发/覆盖/删除）尽量后置并前置确认要求。

**执行护栏参数（每步级 · 与全局约束互补）**：每步写重试上限与超时；错误分类处理——限流/超时/瞬时错（429/503）按退避重试，无效请求/鉴权失败（400/401）不重试直接升级；循环类步骤设迭代上限（防静默空转）。上下文精简与安全红线（资源异常不静默继续）仍生效，本步参数只细化单步行为。

**计划 vs 执行边界**：本步产出执行计划（静态、可审阅、可审批）；7a 建 Run 按计划执行（动态）——执行中错误先按第 4 步失败策略处置，策略耗尽才触发 3b/3c 再规划。计划不改，执行不重复制定。
